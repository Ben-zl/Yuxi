# 多部门成员关系与当前部门权限

状态：proposed
类型：architecture
Owner：backend/package/yuxi/storage/postgres/models_business.py

本文面向实现与审查账号、认证和部门权限的贡献者，属于设计决策提案。前置知识是仓库根目录 `ARCHITECTURE.md` 描述的系统架构和[测试规范](../../testing-guidelines.md)。目标是分离全局账号管理与部门成员管理，并支持按当前部门授权；本记录不声明功能已经实现。

## 问题

现有 `User.department_id` 表达单一部门归属，`User.role` 同时承担全局身份和部门管理角色。认证依赖直接读取这两个字段，设置面板向部门管理员展示用户管理，账号接口允许部门管理员创建、修改和删除普通用户。这些语义无法表达同一用户在不同部门担任不同角色。

部门共享已用于模型、MCP、知识库等资源。多部门支持必须贯通认证、资源可见性、任务提交和执行上下文，不能仅扩展用户表或隐藏页面入口。

## 提案

### 身份与成员关系

PostgreSQL 保存账号、全局超级管理员身份和独立的部门成员关系。成员关系以用户和部门的组合作为唯一键，部门内角色只有 `admin` 和 `user`。普通账号可以加入多个部门，各部门角色互不继承。全局账号身份与请求中的有效部门角色分离；不得通过临时修改 ORM 用户字段投影当前权限并意外写回账号。

超级管理员可以管理和切换任意存在的部门，无需创建自己的部门成员关系。部门成员角色编辑不提供 `superadmin`，也不能改变目标账号的全局身份。

添加成员只关联已有有效账号，默认角色为普通成员；重复添加不能产生重复记录或覆盖已有角色。移除成员只解除该部门关系，不删除账号、其他部门成员关系或业务资源。账号删除仍属于超级管理员独占的用户管理能力，删除后凭证与成员授权失效。

新建普通账号不强制加入部门；无部门账号可以登录和管理个人资料，但不能访问需要部门上下文的资源。登录后有可用部门时选择一个有效部门，无可用部门时展示无部门状态，不静默加入默认部门。创建部门仍可复用现有创建管理员账号的流程，但部门管理员身份落在成员关系上。

### 删除部门边界（待用户确认）

推荐保留超级管理员删除部门的能力，但不再把用户迁入默认部门，也不级联删除账号。若目标部门仍有业务资源归属、共享引用或未结束任务，拒绝删除并返回阻止删除的原因；本功能不自动清理、迁移或重新归属这些资源。满足删除条件后，只删除目标部门及其成员关系，撤销绑定该部门的凭证，保留用户账号及其其他部门关系。原有默认部门禁止删除规则保持不变。

部门删除后，仍指向该部门的登录上下文在下一次请求失效，前端清理旧部门视图并引导重新选择。这一新增数据边界需要用户确认后才能进入实施计划。

### 权限边界

| 能力 | 超级管理员 | 当前部门管理员 | 普通成员 |
|---|---|---|---|
| 用户管理页面及账号创建、修改、删除接口 | 允许 | 拒绝 | 拒绝 |
| 当前部门成员管理列表 | 允许 | 允许 | 拒绝 |
| 添加已有账号为普通成员 | 允许 | 允许 | 拒绝 |
| 移除当前部门普通成员 | 允许 | 允许 | 拒绝 |
| 任命、降级、移除部门管理员 | 允许 | 拒绝 | 拒绝 |
| 切换部门 | 任意存在的部门 | 自己加入的部门 | 自己加入的部门 |

部门管理员不能修改自己或其他部门管理员的角色、不能移除部门管理员、不能编辑任何账号的资料或密码。个人资料自助修改保留现有边界，不归入管理他人账号的接口。

成员添加使用独立的已有账号检索能力，仅向有权管理目标部门的操作者返回添加所需的账号 ID、登录 ID 和显示名称；不复用超级管理员的完整用户管理响应，不暴露密码、手机号或其他部门角色。部门管理员添加一个在别处担任管理员的账号时，该账号在目标部门仍默认是普通成员。

超级管理员可以移除或降级部门的最后一位部门管理员，后续仍可凭全局权限管理该部门；部门管理员无此能力。全局超级管理员的管理权限不能通过部门成员操作撤销。

### 当前部门与执行上下文

当前部门属于登录会话的请求上下文，不是用户账号上的全局可变字段。切换部门不改变同一账号其他独立登录会话的部门；共享同一登录凭证的浏览器标签页按同一会话处理。

认证边界先验证账号，再从 PostgreSQL 校验目标部门、成员关系及当前角色，产生用户身份、当前部门和有效权限上下文。客户端提供的部门 ID 或旧凭证中的角色不能替代服务端授权。不存在的部门拒绝访问，非成员切换或越权成员操作拒绝访问。

成员移除和角色修改在事务提交后影响后续请求；旧凭证不能保留已撤销的管理权限。若当前部门已不可访问，前端清除相关视图和数据并要求重新选择；没有其他部门时进入无部门状态。切换失败保持原有效上下文，不展示部分切换状态。

切换成功后重新加载部门相关列表、权限和界面入口，清理旧部门缓存，并阻止切换前发出的迟到响应覆盖新部门状态。部门授权消费当前部门，而不是把用户全部部门的权限合并；现有全局共享和个人资源语义保持不变。

请求接入通过既有 `RunSubmissionCommand` 链路固定提交部门，持久化事实并由 worker、AgentScope 配置投影和下游工具消费。切换页面部门不改变已经提交或排队任务的部门、资源凭据及产物归属。后续执行仍遵守有效授权检查，固定部门不等于固化永不过期的成员权限。

挂起任务恢复必须使用原任务所属部门并重新校验该部门权限，不能把恢复请求所在页面的部门当作原任务部门。当前 `agent_router.py` 的 resume 分支直接创建 Run，实施计划需要单独覆盖此分支，不能假定普通提交链路的变更自动生效。

API Key、CLI、Channel 和定时任务等非交互入口必须使用各自明确绑定或提交时记录的部门上下文，不读取某次 Web 登录的活动部门，也不合并成员部门；没有有效部门上下文时拒绝部门级操作。具体接口签名及上下文传递位置在实现计划中对照现有调用链确定，不新增旁路提交机制。

### 页面与组件

设置面板的桌面和移动入口均只向超级管理员展示“用户管理”，内容挂载、可选标签和直接打开入口执行同一限制。后端接口独立实施授权。

设置面板增加“成员管理”，仅当前部门管理员和超级管理员可见。列表展示名称、登录 ID、部门内角色和允许的操作，支持加载、空列表、查询失败和操作失败状态。添加已有账号默认使用普通角色；超级管理员可以编辑普通成员与部门管理员角色，部门管理员只看到角色展示，不提供无实际变化的角色编辑按钮。写入成功后使用后端结果刷新列表。

左下角登录菜单展示当前部门和有效角色，增加“切换部门”。超级管理员选择任意部门，其他用户选择自己的成员部门。超级管理员通过切换部门管理目标部门成员，成员管理面板不再维护另一个与当前上下文冲突的部门选择器。

### 分层与事务

HTTP 路由负责请求解析、认证和响应；成员添加、移除、角色修改和部门切换的用例位于 `yuxi.services`，持久化查询和唯一性约束位于 repository 与 PostgreSQL。跨 repository 的写操作由同一用例事务提交，日志与事实保持一致。

现有认证依赖和资源查询统一消费有效权限上下文；前端 store 保存后端返回的身份、当前部门、可切换部门及角色。数据库迁移仅演进 schema，不在 API 启动或迁移脚本中夹带开发账号清理。

### 开发数据与非目标

开发环境执行一次性非超级管理员账号清理，保留所有超级管理员账号及其数据。清理只处理账号、成员关系和必要的凭证失效，不删除、迁移或重新归属历史会话、文件、智能体、知识库等业务数据，不删除部门。历史非超级管理员业务数据的可用性不作为本次验收目标。

清理不调用会级联删除业务数据的通用硬删除流程；优先沿既有软删除语义令账号与凭证失效。执行前核对实际清理范围，执行后回读剩余有效账号、超级管理员数据和凭证失效结果。只保留超级管理员身份所需的 schema 调整，不迁移已清理账号的旧单部门角色。

不新增邀请注册、自定义角色、跨部门权限汇总、历史业务数据兼容层或生产环境自动清理机制。保留仓库内与本功能无关的未提交改动。

## 替代方案

1. 独立成员关系与会话部门上下文：采用。可以表达同一用户在不同部门的不同角色，部门切换不改写账号归属；代价是需要贯通认证、资源查询和任务上下文。
2. 保留全局部门管理员角色，只增加部门 ID 集合：拒绝。无法表达部门内角色差异，容易把一个部门的管理权限传播到其他部门。
3. 每个部门创建一个独立账号：拒绝。不满足同一账号加入多个部门和登录菜单直接切换的目标，并重复维护个人身份。

## 风险

认证依赖当前返回 ORM 用户，已有消费者直接读取 `role` 和 `department_id`。遗漏任一读取点都可能造成跨部门授权或旧单部门语义残留；实现计划必须覆盖 Web、资源查询、API Key、CLI、Channel、定时任务和 worker，而不是只调整成员页面。

部门共享资源和任务执行涉及不同生命周期。需要固定提交部门，同时按真实授权边界处理成员关系撤销；不能通过动态读取用户当前部门来规避权限失效问题。

成员更新和管理员写操作可能并发。授权检查与成员变更需要由 service 的事务边界统一处理，避免读到旧角色后完成越权写入；新增关系依赖数据库唯一约束。

开发账号清理不处理历史业务数据，因此会保留不可再由原账号访问的资源。此代价仅适用于当前开发环境，不构成生产迁移方案；清理不能通过删除部门、重置数据库或级联删除业务对象来完成。
